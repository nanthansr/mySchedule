01 The Problem
Credit card fraud detection is a canonical hard ML problem: extreme class imbalance (~0.17% fraud rate), high cost of false negatives, real-time latency requirements, and production environments where model behavior must be continuously monitored.

The goal was to build a production-grade MLOps pipeline — not just a Jupyter notebook with a model. The project needed to demonstrate every component that appears in real MLOps engineering JDs:

  • ✓ REST API serving layer (not batch inference)
  • ✓ Experiment tracking and model artifact versioning
  • ✓ Automated CI/CD pipeline (test → retrain → build → push)
  • ✓ Model monitoring with drift detection
  • ✓ Infrastructure observability (Prometheus + Grafana)
02 Architecture
All components run in Docker Compose. The serving layer, MLflow server, and monitoring stack are separate containers communicating over a shared Docker network.

03 Tools Chosen & Why
XGBoost
ML Model
Fraud detection is a structured tabular problem. XGBoost consistently outperforms deep learning on tabular data and handles class imbalance through scale_pos_weight. Trains in seconds, not hours. Interpretable feature importance. Correct evaluation: AUC-PR, not accuracy — because 99.8% of samples are negative.
Alternatives considered: LightGBM (similar performance, less ecosystem), RandomForest (slower, less regularization control), sklearn LogisticRegression (too simple for this dataset).
FastAPI
Serving Layer
FastAPI's async-first design and automatic OpenAPI docs are production-grade defaults. Uvicorn provides ASGI performance. The /predict, /health, and /metrics endpoints cover the three things you need in any production ML service: inference, liveness, and observability.
Alternatives: Flask (synchronous, no native async), BentoML (opinionated, heavy), TorchServe (overkill for sklearn/XGBoost).
MLflow
Experiment Tracking
MLflow is the de-facto standard for experiment tracking in open-source MLOps. It handles run logging, artifact storage, and model versioning with zero configuration — just point it at a local directory. The Model Registry provides explicit stage gates (None → Staging → Production).
Alternatives: Weights & Biases (SaaS, great UI, requires account), DVC (Git-based, better for data versioning), Neptune.ai (commercial).
Prometheus + Grafana
Observability
Prometheus pull-model fits containerized apps perfectly — no agent needed. The prometheus_client Python library exposes custom model metrics (fraud rate, prediction latency) alongside default process metrics through the same /metrics endpoint. Grafana provides the dashboard layer. This mirrors what enterprise teams do with Datadog or Dynatrace — same primitives, self-managed.
Alternatives: Datadog (commercial, $$$), New Relic (commercial), custom logging only (no alerting).
GitHub Actions
CI/CD
GitHub Actions is the industry standard for open-source CI/CD. The pipeline runs: pytest → MLflow training run → Docker build → Docker push. The deliberate architecture choice was to retrain in CI as an intermediate step, producing a new model artifact that gets packaged into the Docker image.
Alternatives: Jenkins (self-hosted, operational overhead), CircleCI (similar, less free tier), GitLab CI (locked to GitLab).
Docker Compose
Orchestration
For a 4-container stack (FastAPI, MLflow, Prometheus, Grafana), Docker Compose provides exactly the right level of orchestration — no Kubernetes overhead for a single-node dev/demo environment. The compose file defines service dependencies, shared volumes, and the Docker network in ~60 lines.
Next step: Cloud Run (GCP) for the serving layer, removing the single-host constraint. Then Kubernetes for orchestration at scale.
04 What Failed — Honest Engineering Log
Production systems fail in ways notebooks don't. Here's what actually went wrong and what it taught me.
Model artifact path was hardcoded in the Docker image
Early versions baked the model .pkl path as an environment variable that pointed to a local path. When the container ran, the path didn't exist — model failed to load silently, returning 500 on every predict request.
Fix: MLflow artifact URI is now passed at container start via MODEL_URI env var. The serving layer loads the model dynamically from the MLflow tracking server on startup.
Prometheus metrics endpoint caused race condition on startup
FastAPI tried to register Prometheus metrics before the prometheus_client registry was initialized, causing ValueError: Duplicated timeseries on hot-reload during development.
Fix: Moved metric instantiation to module level (not inside request handlers). Used if not REGISTRY._names_to_collectors guard for dev reload compatibility.
Class imbalance wasn't caught until after first training run
First training run reported 99.8% "accuracy." The model was predicting all-negative — and that prediction was technically correct 99.8% of the time. AUC-ROC looked fine at 0.72. It wasn't. AUC-PR was 0.11 — the model was useless.
Fix: Added scale_pos_weight = (n_negatives / n_positives). Switched primary metric to AUC-PR. Logged both to MLflow for every run. Final AUC-PR: 0.87.
GitHub Actions couldn't authenticate to Docker Hub
Secrets were set as repo environment variables but referenced as $DOCKER_TOKEN (shell syntax) instead of ${{ secrets.DOCKER_TOKEN }} (Actions syntax). The workflow failed with unauthorized — confusing because the credentials were correct.
Fix: Used correct Actions expression syntax throughout. Added a step to verify Docker login succeeded before building the image.
05 Metrics & Results
0.87 AUC-PR (precision-recall curve) — primary metric
0.94 AUC-ROC (secondary metric)
0.17% Dataset fraud rate (class imbalance)
<20ms p95 inference latency (single prediction)
4 Docker containers (FastAPI, MLflow, Prometheus, Grafana)
100% CI pipeline test coverage on model + API
Why AUC-PR and not accuracy? When 99.8% of samples are non-fraudulent, a model predicting "not fraud" for every transaction achieves 99.8% accuracy and 0% utility. AUC-PR measures how well the model ranks the positive class — it's sensitive to false negatives in a way accuracy is not. This is the answer you give in an interview when asked about evaluation metrics.
06 Incident Simulation — Fraud Rate Spike
Scenario: A new fraud pattern emerges over a 4-hour window. Transaction volumes are normal, but the fraud rate climbs from the 0.17% baseline to 2.3%. Here is how the monitoring stack catches it and what the on-call engineer does.
T+0
00:00 UTC
Baseline: Everything nominal
Prometheus shows fraud_rate_pct = 0.18%. Prediction latency p95 = 16ms. No active alerts. Grafana dashboard green.
T+1h
01:00 UTC — Early signal
Fraud rate begins climbing silently
fraud_rate_pct rises to 0.6%. No alert fires yet (threshold is 2σ = ~0.8% for this baseline). Prediction latency unchanged — the model is making predictions fine; the issue is in what it's seeing, not how fast.
T+2h
02:15 UTC — Alert fires
Prometheus alert: fraud_rate_pct > 2σ
Alert rule: fraud_rate_pct > 0.85 for 5m fires. Grafana sends webhook notification. On-call engineer woken at 02:15 UTC. Fraud rate is now 1.2% — 7× the baseline.
T+3h
02:20 UTC — Triage
Engineer investigates: model or data?
Step 1: Check /health — serving layer is healthy, model loaded correctly.
Step 2: Check Grafana — prediction distribution has shifted. The model's confidence scores for fraud are higher than baseline. Input feature distributions have drifted (mean transaction amount ↑ 40%, new merchant category appears).
Step 3: This is a data drift event, not a serving failure. The model is working correctly — it's seeing transactions that look like the fraud patterns it learned. But the scale is unusual.
T+4h
03:00 UTC — Decision point
Escalate vs. retrain decision
Options:
(a) Lower the fraud threshold temporarily to flag more transactions — increases false positives but reduces false negatives during the event.
(b) Trigger an emergency retrain with recent data labeled by the fraud team.
(c) Escalate to fraud operations team to manually review flagged transactions.

Decision: (a) + (c). Threshold lowered via config (no redeploy needed — served as env var). Fraud ops team notified with dashboard link.
T+6h
05:30 UTC — Resolution
Fraud rate returns to baseline
Fraud operations confirmed a coordinated card-skimming attack, now blocked at the card network level. Rate drops to 0.19%. Alert resolves automatically. Postmortem: document the new fraud pattern as a labeled training example. Schedule retrain for next CI run. Restore threshold to default.
What this demonstrates: A monitoring system isn't just graphs — it's a decision-making layer. The value of Prometheus + Grafana here isn't the charts; it's the alert that woke someone up and the dashboard that gave them the context to make the right call in 40 minutes instead of finding out via customer complaints 6 hours later.
07 Interview Signals — How to Talk About This
When asked to walk through a project "I built a production MLOps pipeline for fraud detection — not just the model, but the full stack: FastAPI serving layer, MLflow for experiment tracking, Prometheus + Grafana for model monitoring, and a GitHub Actions CI/CD pipeline that retrains and redeploys on every commit. The interesting engineering problems were around class imbalance, metric selection, and model drift detection."
When asked about observability "I exposed custom model metrics through the same /metrics endpoint Prometheus scrapes — fraud rate percentage, prediction latency distribution, input feature statistics. This mirrors how Datadog or Dynatrace work at enterprise scale. The monitoring stack isn't decorative — it caught a fraud spike before it became a customer-impacting incident."
When asked about class imbalance "The dataset had a 0.17% fraud rate. My first model hit 99.8% accuracy — and was completely useless. I switched the primary metric to AUC-PR, added scale_pos_weight to XGBoost, and went from AUC-PR 0.11 to 0.87. The lesson: metric selection in ML is an architectural decision, not an afterthought."
When asked about CI/CD for ML "The GitHub Actions pipeline runs pytest, then triggers an MLflow training run that logs all metrics and stores the model artifact, then builds a new Docker image with the updated model, then pushes to registry. The deliberate choice was to retrain in CI — not just test. That means every merge to main produces a new deployable model version."
When asked about what you'd do differently "Three things: move the serving layer to GCP Cloud Run to remove the single-host constraint; add Evidently AI for formal drift detection instead of custom numpy code; and implement the MLflow Model Registry with explicit stage gates so nothing goes to production without a registered version. That's my Stage 3."
